# Exporting Sonic planner trajectories for IsaacLab replay

The IsaacLab backend's `trajectory` mode replays the *same* planner output that
MuJoCo executed, so the two engines are compared on identical trajectories.  The
trajectories come from the deploy binary itself — nothing is regenerated by the
evaluation code.

## 1. Run the deploy binary with the planner-motion log enabled

`g1_deploy_onnx_ref` writes the 50 Hz `MotionSequence` to CSV when started with
`--planner-motion-logfile` (see `g1_deploy_onnx_ref.cpp`, the block that dumps
`planner_motion_->BodyPositions / BodyQuaternions / JointPositions`):

```bash
./g1_deploy_onnx_ref lo policy/model.onnx reference/motions/ \
    --planner-file policy/planner_V2.onnx \
    --obs-config policy/observation_config.yaml \
    --input-type zmq_manager --zmq-port 5556 \
    --planner-motion-logfile /tmp/planner_traj/forward_vx+0.60.csv \
    --disable-crc-check
```

One process run = one condition, because the log file is opened once at startup.

## 2. Drive it with a single benchmark condition

```bash
python evaluate_sonic_planner.py --sim mujoco \
    --config configs/walking_eval.yaml \
    --conditions forward_vx+0.60 \
    --output-dir results_traj_export
```

The MuJoCo run produces the metrics for that condition *and* leaves the planner
trajectory in the CSV above.

## 3. Repeat per condition and point IsaacLab at the directory

File names must be `<condition name>.csv` (the names printed by
`--dry-run`).  Then:

```yaml
backend:
  isaaclab:
    mode: trajectory
    trajectory_dir: /tmp/planner_traj
```

## CSV format

One line per 50 Hz frame, comma separated, trailing comma:

```
body_x, body_y, body_z, quat_w, quat_x, quat_y, quat_z, q0 ... q28
```

Joint angles are in **MuJoCo order** (the writer indexes with
`isaaclab_to_mujoco`).  Blocks are separated by a blank line — one block per
replan snapshot of the whole buffer; `load_planner_motion_csv(..., block=-1)`
takes the last, most complete one.

> The IsaacLab G1 articulation orders joints differently from MuJoCo.  Verify the
> mapping (`robot.joint_names` vs the MuJoCo model's joint order) before trusting
> replay results; a wrong permutation looks like a planner regression.
